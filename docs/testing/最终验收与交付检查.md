## 3 60客户端负载

环境：Windows11 10.0.26200，AMD Ryzen5 7640HS，6核12逻辑处理器，约15.2GiB内存，Python3.14.7，SQLite3.53.1。客户端与单实例服务同机回环网络，生产Waitress，SQLite默认DELETE日志、外键及5000毫秒busy_timeout；模拟专用库。操作包含同时开始作答、保存、最终化、每3秒观看演示，以及教师统计和组卷。不代表60名真实学生或真实局域网。

首次16线程完整测试持续604.1秒，0请求错误、60份提交一致，但开始作答p95=1247.2毫秒，超过普通接口1秒目标；30秒复测为1332.3毫秒。失败不能因脚本退出0而忽略。随后使用4线程进行短测，开始作答p95=272.7毫秒，再执行完整60客户端、3秒轮询、610.3秒测试，结果如下。

最终0请求错误，60/60提交一致，50轮教师查询。README把Waitress线程明确为4，未改数据库日志模式或业务算法；此配置减少本次SQLite集中写入时的等待，不推定增加线程就能提高吞吐。原始失败、短测与最后完整记录分别保存：[首次失败](最终证据/perf-first.json)、[16线程短测](最终证据/perf-burst-baseline.json)、[4线程短测](最终证据/perf-burst-four-threads.json)、[4线程最终](最终证据/perf-four-threads-final.json)。组卷只有3次样本，不能据此推定所有题库规模的尾延迟。
